# Add TALA SSO to a project

Follow the guides in this repo instead of writing OAuth code from scratch. Do not invent
endpoints or skip the security settings.

Read first: `tala_sso_integration_guide.md` (contract, Laravel and React) and
`private-repo-access.md` (SSH access to the private SDK repos). Placeholders in those docs
(`https://tala.example.com`, `<owner>`) must be replaced with the real values from the user,
never guessed.

## 0. Rules

- Never print, commit or log a client secret, `.env` file, token or real hostname.
- Never push, deploy or run migrations on production without the user's explicit approval.
- Do not change an existing working integration's behaviour without saying so first.
- TALA's `id` is the stable user key. Never link or look up local users by email.
- Reject a profile with no `id`. If a team allow-list is configured, reject a missing or
  unlisted `team`.

## 1. Detect the stack

| Signal | Stack | What to use |
| --- | --- | --- |
| `composer.json` with `laravel/framework` | Laravel backend | `tala/sso-laravel` package (guide section 1) |
| `package.json` with `react` or `next` | React/Next.js frontend | `@tala/sso-react` (guide section 2) |
| `requirements.txt`/`pyproject.toml` with `fastapi` | FastAPI backend | `recipes/fastapi` |
| Anything else (Django, Flask, Node, ...) | No recipe yet | Stop and tell the user; do not improvise. |

A project can be both (for example a Laravel API plus a React app in separate folders).
Handle each folder separately.

Also check whether SSO already exists (`grep -ri "oauth/authorize\|tala"`). If it does, this is
a review or upgrade, not a fresh install: compare against the checklist in step 5.

## 2. Gather facts from the user

Ask only for what you cannot read from the project:

- The TALA base URL, and the OAuth client ID registered for this app. The secret goes in the
  environment by the user, not in chat.
- The frontend callback URL (the redirect URI registered in TALA, matched exactly).
- Whether to restrict to certain TALA teams (`TALA_ALLOWED_TEAMS`).
- Where users are stored and how sessions work (Sanctum, JWT, cookies).
- Whether the build host can read the private repos over SSH. If it cannot (for example
  Vercel), use a tarball: `npm pack "git+ssh://git@github.com/<owner>/sso-react.git#<tag>"`,
  commit the `.tgz`, and depend on `file:vendor/<name>.tgz`.

## 3. Apply

**Laravel:** add the `vcs` repository with the SSH URL, `composer require tala/sso-laravel`,
publish the config, write the login handler keyed on a `tala_id` column (nullable, unique;
backfill existing users by email once, after a database backup), set the env vars, and make
sure the cache driver is shared and not `array`. Add the logout resolver if the app has logout.

**React/Next.js:** install `@tala/sso-react` at the latest release tag, add the callback route
that renders `<TalaCallback />`, and the sign-in page with `<TalaLoginButton />` pointing at the
backend `/api/auth/tala/redirect`. The button's `onSuccess` posts `{code, state}` to
`/api/auth/tala/callback`.

**FastAPI:** copy `recipes/fastapi/tala_sso.py` into the project, wire the router from
`example_app.py`, implement `login_handler`, and use a shared (Redis) state store if more than
one worker runs.

## 4. Register the client in TALA

The user does this in the TALA dashboard: create the OAuth client, add the exact callback URL,
copy the client ID and secret into the backend environment.

## 5. Checklist (contract)

First run the black-box script against the running backend (local or staging):
`python conformance/check_tala_sso.py http://localhost:8000`. It covers the redirect, PKCE,
state and callback error items. It cannot see inside the app, so verify the rest below by
reading the code.

Verify each item by reading the code or running the app; say which you could not verify.

- [ ] State is generated by the backend, stored server-side, expires, and is single use.
- [ ] A callback with an unknown or missing state is rejected.
- [ ] PKCE S256 challenge is sent on authorize and the verifier on token exchange.
- [ ] The code exchange and profile fetch happen on the backend; the secret never reaches the browser.
- [ ] A profile without `id` is rejected.
- [ ] Local users are matched by `tala_id`, not email.
- [ ] If `allowed_teams` is set, a missing or unlisted `team` is rejected.
- [ ] Only safe messages reach the browser; other errors are logged.
- [ ] The popup callback posts only to the app's own origin, and the opener checks the origin,
      the popup source and `state`.
- [ ] Logout revokes the TALA token (if the app has logout).
- [ ] The login popup opens directly on click (no popup blocker error in a normal browser).

## 6. Finish

Report what changed, what was verified, and what is left for the user (client registration,
env vars, deploy, a real login test). Do not mark the work done on the strength of a build
passing; a successful login in a browser is the real check.
